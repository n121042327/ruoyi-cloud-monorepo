# 移动端与 ToC 扩展位置

首轮**不实现**移动端与 ToC（校外老师 / 校外学生 / 家长端），本文件只定"将来在哪扩"，避免首轮做错决定把扩展位堵死。

## 1. 首轮的三个预留决定

| # | 决定 | 理由 | 首轮要做的唯一动作 |
|---|---|---|---|
| E-01 | 前端保持 **monorepo + `apps/` 并列**（现在是 `apps/plus-ui`），移动端将来是 `apps/pad-teacher` / `apps/pad-student` / `apps/miniapp-parent` | 三个端共享的是**接口契约与类型**，不是页面；放同一个 `apps/plus-ui` 里会让构建产物和路由互相牵扯 | 保持 `apps/` 结构；阶段 6 把教育域的类型与 API 层放在可被复用的位置（`api/edu/**` + `types/edu/**`），不写进页面文件 |
| E-02 | 后端**一套接口**服务多端，不在首轮引入 BFF | 首轮只有 PC 端，BFF 只会多一层没有收益的转发；多端差异（字段裁剪、分页大小）可以用同一接口的参数与权限表达 | 阶段 5 的 OpenAPI 不写"仅 PC"的假设；分页、排序、字段裁剪都走显式参数 |
| E-03 | 家长端的**账号模型**首轮就定下（`edu_guardian` + `edu_student_guardian`，平台级 + 多对多 + 学校侧审核），端不做 | 账号模型是数据模型的一部分，后补会改表、改权限、改绑定流程；端只是消费它 | 表结构与关系在阶段 5 建出来（`05-data-ownership.md` 已列入 5-0 批次）；端不建页面 |

## 2. 各端的扩展位

| 端 | 何时做 | 复用 | 需要新增的内容 |
|---|---|---|---|
| Pad 教师端 | 首轮之后 | 复用 `/edu/**` 接口、教师身份与数据范围（`DS-04` ~ `DS-07`） | 新增 `apps/pad-teacher`；可能需要"离线缓存 + 弱网重试"的接口语义（届时走 ADR） |
| Pad 学生端 | 首轮之后 | 复用选科接口（`getMyStream` / `submitMyStream` / `updateMyStream`）与学生身份（`DS-08`） | 新增 `apps/pad-student`；学生端的登录态与设备绑定策略需单独 ADR |
| 家长小程序 | 首轮之后 | 复用监护人账号模型与 `DS-09` 范围 | 新增 `apps/miniapp-parent`；微信登录与手机号绑定需单独 ADR（涉及外部依赖） |
| ToC（校外老师 / 校外学生） | 规划阶段之后 | 复用租户模型（ToC 是"个人租户"或"机构租户"的变体）、学段 / 学科 / 年级字典、导入导出与异步任务 | **需要一张独立的产品与权限模型**：ToC 没有"学校"这一层，`DS-04` ~ `DS-07` 全部不适用，需要新的范围类型（如 `self_org`）。首轮只做架构预留，不建表、不建接口 |

## 3. ToC 的库表预留策略（不做实现）

| 项 | 首轮处理 |
|---|---|
| 表结构 | **不建**。ToC 的表结构需要它自己的 PRD 与数据范围模型；提前建表会产出没有规则约束的空表 |
| 命名空间 | 预留 `toc_` 前缀（与 `edu_` 并列），避免将来与教育域表混淆 |
| 租户模型 | `sys_tenant.tenant_type` 目前有 `operator` / `group` / `school` 三个取值；ToC 将来新增取值（如 `personal` / `institution`）时，**只加枚举值、不改表结构** |
| 权限模型 | `05-permission-matrix.yaml` 的 `data_scope_type` 枚举已含 `platform` / `tenant_org` / `group_own` / `tenant_subtree_org` / `school` / `grade` / `class` / `teaching_class` / `self` / `self_children`；ToC 新增范围类型时按同样方式扩枚举 |
| 数据隔离 | ToC 与 ToB 共用一套租户隔离机制，不新建一套 |

## 4. 首轮必须避免的三个做法

| 避免 | 为什么 |
|---|---|
| 把移动端页面目录塞进 `apps/plus-ui` | 构建产物、路由守卫、依赖版本会被两端的不同节奏拖着走；monorepo 的目的就是让它们并列 |
| 为首轮 PC 端写"PC 专用"的接口形态（例如接口返回已经拼好的表格列） | 多端会各自需要不同形态，届时只能加接口或加分支 |
| 提前给 ToC 建表 | 没有 PRD 与数据范围约束的表必然要重做，且会污染教育域的数据归属表（`05-data-ownership.md` 的 33 张表会变成 40+ 张没规则的） |

## 5. 结论

- 三个扩展位（前端 `apps/` 并列、后端一套接口、家长账号模型首轮已定）都已在首轮定好，且不需要首轮写移动端代码。
- ToC 只做架构与命名空间预留（`toc_` 前缀、租户类型与数据范围的枚举扩展位），**不建表、不建接口**——这与用户"可以规划、设计架构以及库表结构，但不实现"的要求一致：表结构留到 ToC 自己的 PRD 冻结后再建。
- 首轮避免的三个做法（移动端页面混进 `plus-ui`、PC 专用接口形态、提前建 ToC 表）都已写进本文件，作为阶段 6 / 7 的评审检查项。
