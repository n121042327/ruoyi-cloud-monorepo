# 系统上下文

## 1. 系统是什么

K12 教育 ToB 平台：给**基教集团、学校、校外机构**提供教学管理能力，首轮交付
「年级 / 班级 / 教师 / 学生」四项核心管理以及支撑它们所必需的能力（学校、学年学期、学科配置、教育角色、任教关系、
租户接入、升班与学籍异动、3+1+2 选科、教学班、导入导出与异步任务、审计）。

部署形态：**单机房私有化 + Docker 编排**（`stack-lock.md`：Docker 不可变更），PC 端 B/S 架构。

## 2. 参与方与职责

| 参与方 | 关心的数据 | 在系统里的身份 |
|---|---|---|
| 平台运营方 | 全平台（用于支撑与排障） | 运营方租户（超级租户），`DS-01` |
| 基教集团 | 集团自有组织与配置 | 集团租户，`DS-03` / `DS-10` |
| 学校（校领导 / 教务主任 / 年级主任 / 班主任 / 任课教师） | 本校 / 本年级 / 本班 / 任教班级的教学数据 | 学校租户，`DS-02` / `DS-04` ~ `DS-07` |
| 学生 | 本人的在校记录与选科 | `DS-08` |
| 家长（后续小程序） | 本人子女的在校记录 | `DS-09`，首轮不实现端 |

角色与数据范围的权威定义见 `docs/10-prd/05-permission-matrix.yaml` 与 `08-data-scope-model.md`，
本文件不复制，只说明它们在架构上的落点（见 `09-permission-architecture.md`）。

## 3. 系统边界

### 3.1 系统负责（首轮）

| 能力 | 归属模块 |
|---|---|
| 租户接入、学校与校区、学年学期、学科与配置 | `school` / `term` / `subject` |
| 学生主体与在校记录、监护人、学籍异动 | `student` / `promotion` |
| 教师主体、教育角色、任教关系 | `teacher` |
| 年级、班级、花名册、班主任、教学班容器 | `grade` / `class` |
| 升班（按学年追加，不改历史） | `promotion` |
| 3+1+2 选科、变更申请与审批、组合分布统计 | `stream` |
| 导入导出、异步任务中心、死信与重放 | `import-export` |
| 操作日志、敏感数据访问日志、运营访问留痕、归档 | `audit` |

### 3.2 系统不负责（周边）

| 周边 | 与系统的关系 | 首轮处理方式 |
|---|---|---|
| 统一身份认证（学校已有 SSO / CAS） | 期望对接，但不阻塞交付 | 首轮用平台账号（`s+学号` / 教师工号），预留 `sys_user` 外部标识字段与登录扩展点；对接方案属后续 ADR |
| 短信 / 家校通知 | 用于激活码分发、审批通知 | 首轮不做短信通道：激活码由班主任打印密码条分发（D-039）；通知只做站内提示 |
| 文件存储 | 导入文件、导出结果、失败明细 | 首轮用 RuoYi 的 `ruoyi-common-oss` 抽象；私有化环境用本地/NAS 存储，不落地应用服务器临时目录（`REQ-IMP-045`） |
| 题库 / 作业 / 考试 / 练习 / 错题 / 学情分析 | 后续阶段的核心业务 | 首轮**只预留模块位与扩展点**（`03-module-division.md` 第 6 节），不设计表、不建接口 |
| 统一消息网关 / 钉钉 / 企业微信 | 后续可能的通知渠道 | 不做，通知能力收敛在站内 + 轮询任务中心 |
| 外部学籍系统（全国学籍号校验等） | 期望数据一致 | 首轮只做字段与格式校验（`BR-STU-022`），不做在线校验 |

## 4. 外部依赖与失败影响

| 外部依赖 | 用途 | 不可用时的表现 | 首轮缓解 |
|---|---|---|---|
| MySQL 8 | 全部业务数据 | 系统不可用 | 单机房 + 定期备份（`NFR-DATA-*`） |
| Redis | 权限解析缓存、热点缓存、令牌 | 降级为直查数据库（性能下降但不越权） | 缓存只存"解析结果"，不存权威数据（`08-cache-strategy.md`） |
| RabbitMQ | 异步任务、削峰 | 异步接口入队失败 → 前端提示可重试，排队中的任务保留 | 死信 + 重放（`REQ-IMP-038`），日志写入失败进入只读降级（`REQ-AUD-037`） |
| 文件存储 | 导入文件与结果文件 | 导入 / 导出不可用，其余功能正常 | 文件引用与业务解耦，数据库只存引用（`REQ-IMP-041`） |
| Elasticsearch | 题库检索（后续） | 首轮不启用，无影响 | 首轮不引入 |

## 5. 信任边界

| 边界 | 说明 | 架构上的落点 |
|---|---|---|
| 客户端 ↔ 网关 | 用户身份与令牌在这里生效 | 网关鉴权（Sa-Token）+ 接口层权限注解 |
| 网关 ↔ 教育域服务 | 可信内网调用，但**仍校验租户与数据范围** | `ruoyi-edu` 内统一的数据权限拦截（`09-permission-architecture.md`） |
| 教育域服务 ↔ 平台侧（运营） | 运营方可见全平台，但**导出需独立授权并留痕** | `DS-01` + `edu_data_grant`（只读授权）+ 审计 |
| 学校租户 ↔ 学校租户 | 默认不可见（不跨校共享业务数据） | 租户隔离 + 无默认下钻 |
| 集团租户 ↔ 下属学校租户 | 集团**不默认**读下属学校教学数据 | 见 `09-permission-architecture.md` 第 6 节 |
| 应用 ↔ 文件存储 | 下载走短时签名、与登录态绑定 | `REQ-IMP-042` |

## 6. 首轮交付范围与"不做的能力"清单

首轮范围以 `docs/10-prd/00-index.md` 与 `01-product-context.md` 为准，架构上体现为三条约束：

1. **单服务优先**：首轮全部教育业务放在 `ruoyi-edu` 一个服务内（`03-module-division.md` 第 2 节），
   避免在需求还在变的时候承担分布式事务与跨服务一致性的成本。
2. **异步只用于耗时与削峰**：导入执行、导出、升班执行、教学班生成、日志归档（`07-sync-async-boundary.md`）。
3. **权限与审计是横切能力**：数据权限与审计不靠"每个接口自己记得写"，而是走统一拦截与统一切面
   （`09-permission-architecture.md` 第 4 节、`07` 第 5 节）。

## 7. 结论

- 上下文清晰：五类参与方、六类信任边界、五个外部依赖都有明确落点。
