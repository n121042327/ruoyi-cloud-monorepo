# 家长绑定与学生数据采集模型

本文档回答三个问题：学生数据由谁录入、班级关系由谁确定、家长如何与孩子建立关联。
文中的表结构是**概念与逻辑模型草案**，用于指导阶段 5 的物理表设计与迁移脚本；
字段类型、索引与约束在阶段 5 定稿。

## 1. 结论先说

| 问题 | 结论 |
|---|---|
| 学生主数据由老师逐个录入吗 | **不是**。批量导入是主路径，老师做的是审核与补充 |
| 班级关系能由家长扫码自选吗 | **不能**。班级关系必须由学校侧产生 |
| 家长扫码做什么 | **认领学生 + 补充资料**，认领需班主任审核 |
| 家长填报的资料直接生效吗 | 不直接生效，走资料变更审核 |

## 2. 学生数据分两层

把字段按"谁说了算"分成两层，是整套流程的基石。

| 层次 | 字段 | 来源 | 权威方 | 能否被家长修改 |
|---|---|---|---|---|
| 主数据 | 学号、姓名、性别、入学年份、学段、年级、行政班归属、学籍状态 | 学校导入 / 教务或班主任批量维护 | 学校 | 否，只能申请修改 |
| 补充数据 | 证件类型与号码、出生日期、监护人信息、联系方式、联系地址 | 家长扫码填报 | 家长填报，班主任审核 | 是，需审核 |

规则：

- 主数据的写入接口只对学校侧角色开放，家长端没有写入口
- 补充数据即使由学校导入，家长也可以申请修正
- 两类数据的修改都进入审计

## 3. 班级关系为什么必须由学校侧产生

如果允许家长自选班级，会同时出现四个问题：

1. 同一名学生被不同家长绑到不同班级，花名册互相矛盾
2. 恶意绑定他人子女，冒领联系信息
3. 学校无法对学籍负责，出问题时责任边界不清
4. 升班、调班、毕业等流程失去可依据的基线

因此：**班级关系是学校的行为，绑定是家长的申请。** 两者通过审核串联。

## 4. 绑定流程

```
① 学校导入学生主数据并完成编班
        ↓
② 班主任在班级详情生成"班级绑定二维码"（带班级上下文与有效期）
        ↓
③ 家长扫码 → 手机号注册 / 登录
        ↓
④ 家长输入学生姓名 + 学号（或证件号后四位）发起认领
        ↓
⑤ 系统校验：该学生确实在本二维码对应的班级内
        ↓
⑥ 生成待审核的绑定申请，进入班主任待办
        ↓
⑦ 班主任 / 教务主任审核通过 → 绑定生效
        ↓
⑧ 家长补充或确认监护人信息、联系方式、地址
        ↓
⑨ 补充数据进入资料变更审核 → 审核通过后写回学生档案
```

### 防滥用的七条约束

| 编号 | 约束 |
|---|---|
| GB-01 | 二维码带班级上下文（租户 + 学校 + 班级）与有效期，默认 7 天，可撤销重发 |
| 2 | 一个学生可被绑定的监护人数默认上限 3，可按学校配置 |
| GB-03 | 一个手机号可绑定的学生数默认上限 5，可按学校配置 |
| GB-04 | 同一监护人与同一学生不允许重复申请；已生效或待审核状态下拒绝再次提交 |
| GB-05 | 认领时必须同时匹配姓名与学号（或证件号后四位），不接受只凭姓名 |
| GB-06 | 绑定申请按班级聚合，班主任可批量审核 |
| GB-07 | 二维码泄露不构成风险：认领仍需匹配到具体学生且需人工审核 |

## 5. 领域模型

```
租户树
  ├─ 运营方租户 ── 数据共享授权(data_grant)
  └─ 学校租户 ── 在校记录(student_school_record) ── 行政班(class)
                        │
                        ├─ 学生资料变更申请(profile_change)
                        └─ 绑定申请(bind_request) ── 班级二维码(qrcode)

平台级主体（不参与学校租户隔离）
  ├─ 学生(student)      ── 一名学生全平台一条，学号全平台唯一
  └─ 监护人(guardian)   ── 手机号全平台唯一

学生(student) ── 在校记录(student_school_record) ── 学校租户
学生(student) ── 监护人学生关联(guardian_student) ── 监护人(guardian)
```

关键点有两个：

1. **监护人位于租户树之上**，不属于任何学校租户。这是"一个家长可以同时是 A 校和 B 校孩子的家长"这一场景的唯一可行解。
2. **学生主体同样是平台级主体**。学号全平台唯一（`D-027`）与跨校转学学号不变（`BR-STU-020`）
   共同要求学生不能按学校租户分裂。学校与学生之间的归属关系由 `edu_student_school_record`（在校记录）承载，
   它才是带 `tenant_id` 的隔离表。见 `D-037`。

## 6. 表结构草案

### 6.1 `edu_student` 学生主体

已在校学生主体表，此处只列与本文档相关的列。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 主键 |
| `student_no` | varchar(32) | 学号，**全平台唯一**（见 BR-STU-001） |
| `national_student_no` | varchar(64) | 全国学籍号，允许为空，非空时全平台唯一（见 BR-STU-022） |
| `student_name` | varchar(50) | 姓名 |
| `gender` | char(1) | 性别 |
| `enroll_year` | smallint | 入学年份 |
| `del_flag` | char(1) | 逻辑删除 |

唯一键：`uk_student_no (student_no)`

**本表不设 `tenant_id`，也不存学籍状态。** 原因见 `D-037`：学生主体是平台级实体，
学籍状态描述的是"在某所学校的学籍期间"，属于在校记录。学校侧读学生必须经在校记录两段式取数。

配套表 `edu_student_school_record`（在校记录）承载带租户隔离的部分：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 主键 |
| `student_id` | bigint | 学生主体（平台级） |
| `tenant_id` | varchar(20) | 学校租户 ID，教学数据隔离键 |
| `school_id` | bigint | 学校 |
| `enrollment_status` | varchar(20) | 学籍状态（转入未报到 / 在读 / 休学 / 出国 / 失踪 / 已转出 / 毕业 / 结业 / 肄业 / 开除 / 退学 / 死亡），共 12 项 |
| `enroll_date` | date | 入学日期 |
| `graduation_date` | date | 离校日期，可空 |
| `is_current` | char(1) | 是否为该学生当前有效的在校记录 |
| `create_by` / `create_time` / `update_by` / `update_time` | | 审计列 |
| `del_flag` | char(1) | 逻辑删除 |

唯一键：`uk_student_school (student_id, tenant_id, enroll_date)`
索引：`idx_tenant_status (tenant_id, enrollment_status)`、`idx_student_current (student_id, is_current)`
外键：`student_id → edu_student.id`（禁止级联删除）

### 6.2 `edu_guardian` 监护人主体（平台级）

**这张表不带 `tenant_id` 隔离**，因为监护人是跨租户实体。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 主键 |
| `phone` | varchar(20) | 手机号，登录名，**全平台唯一** |
| `guardian_name` | varchar(50) | 姓名 |
| `status` | char(1) | 状态：正常 / 停用 |
| `last_login_time` | datetime | 最近登录 |
| `create_time` / `update_time` | datetime | 时间戳 |
| `del_flag` | char(1) | 逻辑删除 |

唯一键：`uk_guardian_phone (phone)`

> 权限提示：该表必须挂在平台级数据权限下，只有运营方与家长本人可读。
> 学校侧只能通过 `edu_guardian_student` 看到"与本校学生有关"的监护人信息，不能全表扫描。

### 6.3 `edu_guardian_student` 监护人与学生关联

## 7. 数据范围如何收窄

监护人跨租户，因此每次查询都必须先定位"本次操作针对哪个孩子"。

```
监护人请求 /guardian/children            → 返回本人全部生效绑定的孩子（跨租户列表）
监护人请求 /guardian/child/{studentId}/* → 校验该 studentId 在本人绑定列表内
                                          然后取该学生"当前有效的在校记录"，把范围切到其所属学校租户
学校侧请求 /edu/student/*                → 走学校租户的常规数据权限
```

硬约束：

| 编号 | 约束 |
|---|---|
| GB-08 | 监护人接口必须先校验绑定关系，再用该学生"当前有效的在校记录"所属学校租户构造范围 |
| GB-09 | 不允许通过"监护人已登录"直接放行跨租户查询 |
| GB-10 | 学校侧读取监护人信息时，只允许读取与本校学生有关联的记录，禁止全表查询 |

## 8. 与首轮的关系

| 项 | 首轮 |
|---|---|
| `edu_guardian` / `edu_guardian_student` / `edu_student_bind_request` / `edu_class_bind_qrcode` / `edu_student_profile_change` | **建表**，进入首轮迁移脚本 |
| 家长端小程序 / H5 | 不实现 |
| 学生端 | 不实现界面，但学生登录名与账号在首轮建立 |
| 二维码生成与认领接口 | 不实现，表结构预留 |

理由：表结构一旦定型再改，代价远高于预留。用户已明确要求"架构与库表结构可以规划、设计，但端不实现"。

## 9. 已确认事项（2026-09-29）

| 编号 | 事项 | 结论 |
|---|---|---|
| GB-11 | 监护人手机号是否作为登录名 | **是**，全平台唯一，即监护人登录名 |
| GB-12 | 一个学生可绑定的监护人数上限 | **3**，可按学校配置（见 GB-02） |

## 10. 多子女场景下的登录态设计

手机号作登录名的直接后果是：**一个家长只有一个账号，却可能对应多个孩子**。
这会带来两个必须明确的问题。

### 10.1 问题一：进入系统后默认看哪个孩子

不能默认"看全部"，因为多个孩子可能分属不同学校甚至不同集团，
把范围并集会模糊数据边界，一旦某个孩子被越权查看，无法判断是哪段范围出的问题。

方案：**登录后先进入"我的孩子"列表，由家长选择其中一个进入**。

```
家长登录
   ↓
我的孩子（列表：姓名 + 学号 + 学校 + 年级 + 班级，不含联系方式与证件）
   ↓
选择某个孩子 → 进入该孩子的页面
   ↓
每次请求都携带"当前孩子"上下文，数据范围按该孩子所属学校租户收窄
```

### 10.2 问题二：能否切换到另一个孩子

可以，但**切换等于换一次上下文**，不是扩大范围。技术上的处理：

| 编号 | 约束 |
|---|---|
| GB-15 | 每次请求必须显式携带 `studentId`，服务端校验该学生在当前监护人的生效绑定列表内 |
| GB-16 | 校验通过后，用该学生当前有效在校记录上的 `tenant_id` 构造本次请求的数据范围，不复用上一次请求的范围 |
| GB-17 | 不允许把多个孩子的范围合并成一个查询，除非这些孩子属于同一学校租户且同一资源类型 |
| GB-18 | "我的孩子"列表接口只返回摘要字段，不返回联系方式、证件号、地址等敏感信息 |
| GB-19 | 前端切换孩子时必须清空上一个孩子的页面状态与缓存，避免串数据 |

### 10.3 跨校与跨集团的处理

| 场景 | 处理 |
|---|---|
| 两个孩子在同一学校租户 | 仍按单孩子上下文处理，不做范围合并，保持实现一致 |
| 两个孩子在不同学校租户（同集团） | 各自独立授权，分别校验绑定关系 |
| 两个孩子在不同集团 | 互不影响，A 集团的绑定不产生 B 集团的任何权限 |

### 10.4 为什么不做"合并范围"

合并看起来体验更好，但会带来三个问题：

1. 越权排查困难——出问题时无法定位是哪段范围被放宽
2. 与 GB-08 冲突——GB-08 要求按"该孩子所属学校"收窄
3. 后续接入更多端（Pad、小程序）时，合并范围的语义会更难维护

因此首轮明确选择**单孩子上下文**，概览信息通过受限的列表接口提供。
