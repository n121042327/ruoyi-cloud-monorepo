# 产品背景与范围

## 1. 问题背景

教育集团在扩张过程中会出现三类管理断裂：

1. **组织单元各管一段**：集团、学校、年级、班级各自维护名单，同一名学生在不同表格里状态不一致
2. **学年切换靠人工**：每年升级、分班、转学、休复学靠 Excel 手工搬运，历史数据被覆盖，追溯困难
3. **权限靠人管**：谁能看到全年级名单、谁能改学生联系方式，全靠口头约定，没有系统约束

现有 RuoYi-Cloud-Plus 基线提供了多租户、用户、角色、菜单、部门等通用能力，
但**没有教育领域的组织模型、学籍模型与选科模型**，也没有能表达"校级 / 年级 / 班级 / 个人"四层的数据权限。

## 2. 产品定位

面向教育机构与教育集团的 ToB 教学管理平台，先把**"谁在学校里、在哪个班、教什么、学什么"**这套主数据做对，
再在此基础上叠加题库、作业、考试、练习、错题与学情分析。

一句话：**首轮解决"人与组织的准确性和历史可追溯"，不解决"教学内容"。**

## 3. 客户与用户

| 层级 | 是谁 | 主要诉求 |
|---|---|---|
| 系统 | 系统超级管理员（`super_admin`）。系统内置账号，不属于任何业务租户 | 部署初始化、应急处理、跨租户排查。不受数据范围与功能权限限制，可执行全部功能，但每一步强制留痕，且禁止用于日常业务操作（`BR-ORG-014`） |
| 运营方 | 产品运营、实施、客服。运营方本身也是一个租户，且是**超级租户** | 开学校租户、开集团租户、查问题、导出数据，且每一步可审计 |
| 教育集团 | 集团管理员、集团专家、集团领导。集团是一个租户，下挂多个学校租户 | 掌握集团整体结构与本级业务数据，不越权看下属学校的教学细节 |
| 学校 | 校领导、教务主任、年级主任、班主任、任课教师。一所学校对应一个学校租户 | 本校数据的准确维护与分级可见 |
| 学生 | 学生（后续 Pad / 移动端）。小学生没有手机号，登录名需单独设计 | 看自己的班、课、选科 |
| 家长 | 家长（后续小程序）。一个家长可能有多个孩子，可能跨班、跨年级、跨校甚至跨集团 | 看自己全部孩子的信息 |

## 4. 首轮范围

### 4.1 交付范围

| 领域 | 包含 |
|---|---|
| 组织 | 租户接入、学校、校区、学年学期、学段与年级、学科 |
| 人员 | 学生、教师、教育角色、任教关系 |
| 编班 | 行政班、教学班、班级花名册 |
| 学籍 | 入学、升班、调班、留级、转入未报到、休学、复学、出国、失踪、转出、毕业、结业、肄业、退学、开除、死亡、跨校转学 |
| 选科 | 3+1+2 选科、选科组合、变更申请与审批 |
| 支撑 | 导入导出、异步任务、审计日志、字典与基础配置 |

### 4.2 明确不做

| 不做 | 原因 | 何时做 |
|---|---|---|
| 自动排课 | 算法与约束复杂，与主数据不是同一层问题 | 后续 |
| 自动优化编班 | 同上 | 后续 |
| 题库 / 作业 / 考试 / 练习 / 错题 / 学情分析 | 依赖主数据先稳定 | 下一阶段 |
| 教师端 Pad、学生端 Pad、家长小程序 | 需要 PC 端先跑通 | 后续 |
| ToC 校外师生 | 商业模式与数据合规待定 | 只做架构与预留 DDL |
| 自动化的跨校教学资源（题库习题、试卷）共享 | 共享必须由运营方逐条显式授权，且只读，不做按租户树的自动下钻；学生、班级、教师、成绩等业务数据不跨校共享 | 不做，改为运营方授权 |

## 5. 成功指标

| 编号 | 指标 | 目标值 | 度量方式 |
|---|---|---|---|
| CTX-GOAL-01 | 学生主数据准确率 | 学校自评 ≥ 99% | 抽样比对导入结果与学校花名册 |
| CTX-GOAL-02 | 学年升级可追溯 | 100% 历史班级关系可回溯到任一学年 | 查询历史学期班级关系，缺记录即失败 |
| CTX-GOAL-03 | 越权访问 | 0 例 | 覆盖跨租户、跨校、跨年级、跨班、ID 猜测的测试全部通过 |
| CTX-GOAL-04 | 关键页面响应 | 查询 P95 ≤ 1 秒 | 在 65 校 / 10 万学生 / 200 并发模型下压测 |
| CTX-GOAL-05 | 批量导入可用性 | 5000 行学生名单单次导入成功 | 端到端导入测试 |
| CTX-GOAL-06 | 操作可审计 | 关键写操作 100% 有日志 | 抽查审计表 |

## 6. 约束

| 类型 | 约束 |
|---|---|
| 技术 | 复用 RuoYi-Cloud-Plus 2.6.2 基线，JDK 17，Vue 3 + Element Plus，不改基线版本 |
| 部署 | Docker 化，私有化部署为主，客户环境可能内网 |
| 数据 | 教育表与系统表同库但服务边界分离，禁止跨服务直接读写对方表 |
| 合规 | 学生个人信息（身份证号、手机号、监护人信息）需最小化采集、脱敏展示、操作留痕 |
| 规模 | 单租户最大 65 所学校、10 万学生、200 并发活跃用户 |

## 7. 量化业务事实（已确认）

以下为已与用户确认的口径，模块 PRD 与表结构必须遵守：

| 项 | 口径 | 影响 |
|---|---|---|
| 租户模型 | 租户即组织单元，分学校租户、集团租户、运营方租户三类；上下级关系为 运营方 → 集团 → 学校，不超过三级 | 教学数据落学校租户；集团需显式授权才能看下属学校数据 |
| 学号 | **全平台唯一，由系统统一发号**，学校不自编 | 格式为「入学年份 + 全局序号」；导入时忽略源学号，导入后提供学号对照表 |
| 跨校转学 | 允许 | 需要学籍异动表与双方留痕 |
| 学生与行政班 | 同一时间只能属于一个行政班 | 关系表唯一约束 |
| 班主任改监护人信息 | 允许 | 字段级写权限 + 单独审计 |
| 年级与学段对应 | 固定 | 字典固化，不做可配置 |
| 教师跨校任教 | 允许 | 教师与学校多对多，权限按任教学校判定 |
| 班级容量校验 | 不强制 | 编班超容量只提示 |
| 3+1+2 变更 | 学校可配置截止日期，逾期需校级管理员审批 | 选科表含截止时间字段，需要审批流 |

## 8. 假设与风险

### 假设

1. 租户即组织单元：一个学校租户对应一所学校，一个集团租户下挂多个学校租户，三类租户层级不超过三级
2. 学校租户是教学数据的边界；业务数据不跨校共享，跨校可见性只来自平台运营的全平台范围（只读并留痕）与教学资源（题库习题、试卷）的显式共享授权（只读）
3. 学年学期由学校自行维护，集团不做统一校历
4. 学生与教师的账号体系复用现有系统用户，不新建认证体系

### 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 现有租户管理员的放行逻辑可能绕过教育数据权限 | 越权 | 阶段 5 专项核查并改造，见 GAP-004 |
| 学校历史数据格式不统一 | 导入失败率高 | 导入向导提供字段映射与错误逐行反馈 |
| 选科审批流与现有工作流引擎的适配成本 | 进度 | 阶段 4 评估复用 ruoyi-workflow 还是内建轻量审批 |
| 跨校转学涉及两校权限 | 数据泄漏 | 转出与转入分别授权，转学单只暴露必要字段 |
