# 数据范围模型

本文档是权限模型中"能看到哪些数据"的权威定义。
功能权限（能不能做这个操作）见 `05-permission-matrix.yaml`。

## 1. 为什么单独建模

本项目的越权风险集中在数据范围，而不是功能权限。原因有三个：

1. 教育数据的层级天然复杂：租户 → 学校 → 年级 → 班级 → 学生
2. 同一个角色在不同学校可能有不同的范围（教师跨校任教）
3. 现有基线的租户管理员存在放行逻辑，直接套用会放大权限

## 2. 范围类型

| 编号 | 类型 | 含义 | 判定依据 |
|---|---|---|---|
| DS-01 | `platform` | 全平台 | 平台运营角色 + 显式授权项 |
| DS-02 | `tenant_org` | 租户组织结构 | 租户管理员，仅覆盖学校、学年学期、学科、教育角色等组织配置 |
| DS-03 | `group_own` | 集团自有数据 | 集团用户，不包含学校教学数据 |
| DS-04 | `school` | 本校 | 校领导、教务主任的所属学校 |
| DS-05 | `grade` | 所负责年级 | 年级主任的负责年级集合 |
| DS-06 | `class` | 所负责班级 | 班主任的负责班级集合 |
| DS-07 | `teaching_class` | 任教班级 | 任课教师的任教关系集合，且仅限本人所授学科 |
| DS-08 | `self` | 本人 | 学生 |
| DS-09 | `self_children` | 本人子女 | 家长 |

规则 DS-RULE-01：一个用户可同时拥有多个范围，最终可见范围取**并集**。
例如一名教师既是某班班主任，又教另一个班，则可见范围 = 本班 ∪ 任教班级。

规则 DS-RULE-02：范围之间不叠加权限，只叠加可见数据。
若用户只有 `class` 范围，即使具备 `export` 功能权限，导出范围也只能是本班。

## 3. 解析算法

每个请求都必须走同一套解析：

```
输入：当前用户、租户上下文、学校上下文、目标资源类型、目标操作

步骤 1 上下文校验
  缺少 tenant_id                          -> 拒绝（DS-DENY-01）
  目标资源是学校级及以下且缺少 school_id    -> 拒绝（DS-DENY-02）

步骤 2 功能权限校验
  用户是否具备该资源的该操作权限            -> 否则拒绝（不返回数据）

步骤 3 数据范围解析
  收集用户在该资源上的全部范围条目
  解析为空集                             -> 返回空结果，而不是全量（DS-DENY-03）

步骤 4 生成查询条件
  将范围条目转换为查询条件
  多个范围之间用 OR 连接，范围内部用 AND 连接
  范围条件与业务筛选条件是 AND 关系

步骤 5 字段级过滤
  按 field_rules 裁剪返回字段
  敏感字段按 sensitive_fields 掩码
```

## 4. 各资源的范围映射

| 资源 | 主过滤列 | 范围如何落地 |
|---|---|---|
| 学校 | `tenant_id` | 平台运营全量；租户管理员限本租户；其他角色限自己所属学校 |
| 年级 | `tenant_id`, `school_id` | 校领导/教务主任限本校；年级主任限负责年级；其他角色按班级反推 |
| 班级 | `school_id` | 校领导/教务主任限本校；年级主任限本年级；班主任限本班 |
| 学生 | `school_id` | 校领导/教务主任限本校；年级主任限本年级；班主任限本班；任课教师限任教班级且字段受限 |
| 教师 | `school_id` | 校领导/教务主任限本校；教师本人可见自己 |
| 任教关系 | `school_id`, `term_id` | 同班级 |
| 学籍异动 | `school_id` | 同学生 |
| 选科 | `school_id` | 学生限本人；班主任限本班；年级主任限本年级；校领导限本校 |
| 选科变更申请 | `school_id` | 审批人限本校校级管理员 |
| 导入导出 | 同目标资源 | 导出时必须重新解析范围，不复用列表结果 |
| 异步任务结果 | 同目标资源 | 查询结果文件时重新解析范围 |
| 审计日志 | `tenant_id`, `school_id` | 校领导限本校；租户管理员不可见教学类日志；平台运营全量 |

## 5. 强制规则

| 编号 | 规则 |
|---|---|
| DS-DENY-01 | 缺少 `tenant_id` 时拒绝执行任何教育数据查询 |
| DS-DENY-02 | 目标资源为学校级及以下，且角色范围不是 `platform`、缺 `school_id` 时拒绝 |
| DS-DENY-03 | 数据范围解析结果为空集时返回空列表，绝不退化为全量查询 |
| DS-DENY-04 | 导出、文件下载、异步任务结果查询必须重新执行范围解析 |
| DS-DENY-05 | 数据权限独立实现，不继承系统租户管理员的放行逻辑 |
| DS-DENY-06 | 批量操作逐条校验范围，任一条越权则整体拒绝并说明原因 |
| DS-DENY-07 | ID 猜测防护：按 ID 查询详情时，先按范围过滤再按 ID 查询，禁止先查再判断 |
| DS-DENY-08 | 计数、统计、聚合接口同样受范围约束 |

DS-DENY-07 是最容易被写错的一条。错误写法是先取详情，再判断 `school_id` 是否匹配；
正确写法是把范围条件拼进 SQL 的 where 子句，让数据库直接返回空。

## 6. 上下文的传递与隔离

| 场景 | 要求 |
|---|---|
| 单请求 | 租户与学校上下文通过请求级上下文传递，请求结束即销毁 |
| 多标签页 / 多学校切换 | 不得使用用户级共享的动态上下文，避免 A 校请求读到 B 校上下文 |
| 异步任务 | 任务创建时把租户、学校、执行人快照进任务记录；执行时使用快照，不读实时上下文 |
| 消息消费 | 消息体必须携带租户与学校标识，消费端据此构造范围 |
| 缓存 | 缓存键必须带租户与学校前缀；权限判定结果不入缓存 |

## 7. 需要专项核查的现有实现（GAP-004）

阶段 5 开始前必须核查并给出结论：

1. `ruoyi-common-tenant` 的租户切换与上下文存储方式，是否支持请求级隔离
2. 租户管理员是否有绕过数据权限的放行逻辑，边界在哪里
3. `ruoyi-common-mybatis` 的 DataPermission 实现方式，能否表达"学校 + 年级 + 班级"三层
4. 现有缓存键是否带租户前缀

核查结论写入 `docs/40-detailed-design/` 的权限设计章节，并作为后端实现的输入。

## 8. 验收要求

数据范围必须有独立的测试用例集，覆盖：

| 用例类别 | 最少用例数 |
|---|---|
| 跨租户读取 | 每个受保护资源 1 条 |
| 跨校读取 | 每个受保护资源 1 条 |
| 跨年级读取 | 年级、班级、学生各 1 条 |
| 跨班读取 | 班级、学生、选科各 1 条 |
| 任课教师字段限制 | 学生详情 1 条 |
| ID 猜测 | 详情接口 1 条 |
| 批量操作越权 | 1 条 |
| 导出越权 | 1 条 |
| 异步任务结果越权 | 1 条 |
| 空范围返回空结果 | 1 条 |
| 缺上下文拒绝 | 1 条 |
