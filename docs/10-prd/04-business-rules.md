# 业务规则总表

编号规则 `BR-<域>-<三位序号>`。域划分：
`ORG` 组织、`TERM` 学年学期、`SUBJECT` 学科、`GRADE` 年级、`CLASS` 班级、
`STU` 学生、`TEACHER` 教师、`PROMO` 升班与学籍异动、`STREAM` 选科、
`DATA` 权限、`IMP` 导入导出、`AUDIT` 审计。

标注 **[已确认]** 的规则来自用户明确答复，其余为从已确认口径推导、需要用户确认后冻结。

> 2026-09-30 修订：删除残留的旧租户模型表述（"租户下辖多校""学号租户内唯一""跨校转学在同一租户内"等），
> 并收口 `GAP-019` ~ `GAP-021`。相关裁决见 `decisions.md` D-026 ~ D-038。

## ORG 组织与租户

> 2026-09-29 修订：租户模型由"一个租户下辖多所学校"改为"租户即组织单元"。
> 修订原因与影响见 `decisions.md` D-026。

| 编号 | 规则 | 理由 | 影响模块 |
|---|---|---|---|
| BR-ORG-001 | 租户分三类：学校租户（`school`）、集团租户（`group`）、运营方租户（`operator`） | [已确认] | 全部 |
| BR-ORG-002 | 一个学校租户对应一所学校；一个集团租户下可挂多个学校租户；学校租户也可不挂集团独立存在 | [已确认] | 全部 |
| BR-ORG-003 | 租户之间是上下级关系：运营方 → 集团 → 学校，层级不超过三级 | [已确认] | 租户、权限 |
| BR-ORG-004 | 运营方租户是**超级租户**，可查看全平台数据 | [已确认] | 权限 |
| BR-ORG-005 | 超级租户的"查看 / 修改 / 导出"同样是三项独立授权，缺一项即拒绝 | [已确认] | 权限 |
| BR-ORG-006 | 教学数据落在**学校租户**上，学校租户是教学数据的边界。例外：学生主体与监护人主体是平台级实体，不参与学校租户隔离（见 BR-STU-002、BR-ACCOUNT-007） | [已确认] | 全部 |
| BR-ORG-007 | 集团租户用户**不看**下属学校的教学数据；不存在"按租户树自动下钻"的默认行为 | [已确认] | 权限 |
| BR-ORG-008 | 不存在按租户树自动下钻的跨校共享；跨校共享只由运营方逐条显式授权、只读，且**共享对象仅限教学资源**（题库习题、试卷等），不含学生等业务数据 | [已确认] | 全部 |
| BR-ORG-009 | 校区是学校内的位置维度，不改变数据权限边界 | 避免权限模型复杂化 | 学校 |
| BR-ORG-010 | 租户被停用后，其下所有人员登录与写操作被拒绝，历史数据保留 | 数据安全 | 租户、登录 |
| BR-ORG-011 | 学校编码在集团内唯一；无集团的学校租户内唯一 | 便于导入与对接 | 租户 |
| BR-ORG-012 | 每个学校租户记录"根租户"（`root_tenant_id`）：无集团时为自身，有集团时为集团；仅用于统计与授权展开，不参与学号唯一性判定 | 统计与授权需要 | 租户 |
| BR-ORG-013 | 跨校共享由运营方创建授权实现，被授权对象是租户或用户，范围是明确的学校租户集合 + 资源类型集合（仅教学资源） | [已确认] | 权限、租户 |
| BR-ORG-014 | 系统内置超级管理员（`super_admin`）：不属于任何业务租户，不受租户隔离、数据范围与功能权限限制，可执行全部功能、可视同任意角色；其所有访问与写操作**强制写审计且不可关闭**，并禁止用于日常业务操作。它是 `BR-ORG-005`「运营方三项独立授权」的唯一例外 | [已确认] 用户 2026-09-30 指示 | 权限、审计 |

## STU 学生

| 编号 | 规则 | 理由 | 影响模块 |
|---|---|---|---|
| BR-STU-001 | 学号**全平台唯一**，由**系统统一发号**，学校不自编 | [已确认] | 学生、导入、账号 |
| BR-STU-002 | 学生主体是**平台级实体**，不参与学校租户隔离；一名学生全平台只有一条主体记录，跨校转学不新建主体，只新增在校记录 | 保证人员唯一；学号全平台唯一（BR-STU-001）要求主体不能按租户分裂 | 学生、学籍 |
| BR-STU-003 | 一名学生在同一学年学期内只能属于一个行政班 | [已确认] | 班级、学生 |
| BR-STU-004 | 一名学生可同时属于多个教学班 | 教学班语义 | 学生、教学班 |
| BR-STU-005 | 允许跨校转学，转出校与转入校分别保留记录与操作痕迹 | [已确认] | 学籍 |
| BR-STU-006 | 学生主体记录的删除只允许"逻辑删除且不可恢复"，且必须无在读关系 | 保护学籍 | 学生 |
| BR-STU-007 | 学生必填字段：学号、姓名、性别、学段、入学年份 | 主数据最小集 | 学生、导入 |
| BR-STU-008 | 证件号**全平台唯一**，允许为空，非空时唯一 | 主体为平台级，同一人不应因跨校而重复；与 BR-STU-022 全国学籍号口径一致 | 学生、导入 |
| BR-STU-009 | 学生姓名、证件号、手机号在列表与导出中默认脱敏，按权限决定是否展示全量 | 个人信息保护 | 学生、导出 |
| BR-STU-010 | 班主任可修改本人班级学生的监护人信息与联系方式 | [已确认] | 学生、权限 |
| BR-STU-011 | 学生学号一经生成，修改需要校级管理员权限且必须留审计 | 学号是对外标识 | 学生 |
| BR-STU-012 | 学籍状态与班级归属是两个独立维度：**只有在读（`enrolled`）计入在读名单**；休学（`suspended`）、转入未报到（`pending_enroll`）、出国（`studying_abroad`，保留学籍）等非在读状态保留行政班关系但不计入在读名单；复学 / 回国 / 报到后回到在读，复学时需重新确认班级 | [已确认] 用户 2026-09-30 裁决「出国与休学同口径」（`CR-011`） | 学生、学籍、统计 |
| BR-STU-013 | 学生字段分两层：**主数据**（学号、姓名、性别、入学年份、年级、行政班归属、学籍状态）由学校侧产生；**补充数据**（证件、出生日期、监护人信息、联系方式、地址）由家长填报并经审核 | [已确认] | 学生、绑定 |
| BR-STU-014 | 行政班归属只能由学校侧产生，家长端不提供选择班级的入口 | [已确认] 防冒领与数据一致性 | 学生、绑定 |
| BR-STU-015 | 家长填报的补充数据不直接生效，必须走资料变更审核 | [已确认] | 学生、审核 |
| BR-STU-016 | 学生数据以批量导入为主路径，老师负责审核与补充，不要求逐个手工录入 | [已确认] | 学生、导入 |
| BR-STU-017 | 学号格式为「入学年份 4 位 + 全局序号 6 位」，如 `2026000001`；序号按年重置，靠年份前缀保证全局唯一 | [已确认] 可读、可排序、单届容量 100 万 | 学生 |
| BR-STU-018 | 学号一经生成**永不回收、永不重用**；学生删除、转出、毕业后该号作废 | 回收会造成历史混淆 | 学生 |
| BR-STU-019 | 导入学生时**忽略源文件中的学号列**，由系统统一发号；导入完成后提供「学号对照表」下载，供学校回填自有台账 | 学校需要拿到新学号 | 学生、导入 |
| BR-STU-020 | 学生跨校转学时学号保持不变 | 学号由平台发放，与学校无关 | 学生、学籍 |
| BR-STU-021 | 学号允许修改，但需要校级管理员权限且强制留审计；修改后学生登录名同步变化 | 纠错需要 | 学生、账号 |
| BR-STU-022 | 新增 `national_student_no`（全国学籍号）字段，允许为空；非空时全平台唯一 | [已确认] 对外报表与学籍上报需要 | 学生、导入 |
| BR-STU-023 | **转入未报到**：转入校接收学生时，先在该校新建一条状态为 `pending_enroll` 的在校记录；未报到期间不编入行政班、不计入在读名单；学生实际报到后转为在读；始终不报到的，由转入校撤销接收（逻辑删除该在校记录）并留痕，不产生转出记录 | [已确认] 用户要求补充该学籍状态 | 学籍、班级、统计 |
| BR-STU-024 | **开除**：终态学籍状态之一。义务教育阶段（小学、初中）**不得开除**；高中阶段开除需校级管理员审批并留审计。休学期间是否允许开除由学校学生管理部门口径决定，默认允许 | [已确认] 用户要求补充该学籍状态；义务教育阶段限制见《义务教育法》 | 学籍、权限、审计 |
| BR-STU-025 | **出国**：因出国（境）就学办理，**保留学籍**，属非终态；回国后办理复学回到在读 | [已确认] 用户要求补充该学籍状态 | 学籍、班级 |
| BR-STU-026 | **失踪**：学生长期失联时登记，属非终态；找回后复学回到在读；按学校与主管部门口径可转为退学或死亡 | [已确认] 用户要求补充该学籍状态 | 学籍、统计 |
| BR-STU-027 | **结业与肄业**：结业为修完学业但未达毕业标准，肄业为未修完学业而离校；两者都是与毕业不同的终态。**仅高中阶段适用**，义务教育阶段不适用 | [已确认] 用户要求补充；义务教育阶段无这两类出口 | 学籍、权限、统计 |
| BR-STU-028 | **死亡**：终态。登记需校级管理员权限并留存证明材料；死亡学生从常规在读数、在读名单与在校统计中排除，仅在有权限的专门查询中可见 | [已确认] 用户要求补充；不可用退学掩盖，否则退学率失真 | 学籍、权限、审计、统计 |

## PROMO 升班与学籍异动

| 编号 | 规则 | 理由 | 影响模块 |
|---|---|---|---|
| BR-PROMO-001 | 升班是"新增下一学年的班级与学生关系"，不改写历史记录 | [已确认] | 升班 |
| BR-PROMO-002 | 升班必须支持预览、校验、确认、异步执行、结果查看、失败重试 | [已确认] | 升班 |
| BR-PROMO-003 | 升班操作必须幂等，重复提交不得产生重复数据 | [已确认] | 升班 |
| BR-PROMO-004 | 升班批次内，学生默认升入同年级序号 +1 的年级 | 常规路径 | 升班 |
| BR-PROMO-005 | 毕业年级的学生升班结果为"毕业"，学籍状态变更，不再生成下一学年班级关系 | 语义 | 升班、学籍 |
| BR-PROMO-006 | 留级学生不参与默认升级，需在预览阶段显式指定；留级的去向是**目标学年学期的同学段同名年级**（如 2026 级 高一 → 2027-2028 学年 高一），仍不改写源学年记录 | 避免误升 | 升班 |
| BR-PROMO-007 | 调班仅限当前学年学期，更换行政班并保留原关系历史 | 保护历史 | 班级、学籍 |
| BR-PROMO-008 | 休学需记录生效日期与原因；休学期间不计入在读名单 | 语义 | 学籍 |
| BR-PROMO-009 | 复学需校验当前状态为休学，并指定复学后的班级 | 状态机约束 | 学籍 |
| BR-PROMO-010 | 学籍状态共 12 个，其中 7 个为终态：已转出、毕业、结业、肄业、开除、退学、死亡；终态之间不可互转 | 语义 | 学籍 |
| BR-PROMO-011 | 跨校转学在**两个学校租户之间**执行，转出校需先释放行政班关系，转入校接收后才生效；学生主体不迁移，学号不变 | 避免同时占用两校；主体平台级见 BR-STU-002 | 学籍 |
| BR-PROMO-012 | 所有学籍状态变更必须记录：变更类型、生效日期、原因、操作人、原状态、新状态 | 可追溯 | 学籍、审计 |

## DATA 数据权限

|---|---|---|---|
