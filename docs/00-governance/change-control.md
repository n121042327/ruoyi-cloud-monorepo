# 变更控制流程

## 1. 什么时候必须走本流程

以下任一情况成立时必须走变更流程：

- 要修改状态为 `frozen` 的文档或产物
- 要变更 `stack-lock.md` 中"不可变更"的行
- 要调整首轮范围（增加或删除模块）
- 要修改已冻结原型的页面结构、跳转或交互
- 要修改已确认的表结构或 API 契约
- 要调整数据权限模型

## 2. 不允许的做法

- 直接就地覆盖已冻结文件
- 在实现阶段"顺手"改上游设计而不留记录
- 口头说明后不写入文档

## 3. 变更申请模板

写入 `docs/00-governance/change-requests/CR-<编号>.md`：

```markdown
# CR-<编号> <一句话标题>

- 发起人：
- 发起时间：
- 关联 GAP / 需求编号：

## 变更对象

| 文件 | 当前状态 | 变更后状态 |
|---|---|---|

## 变更原因

（触发这个变更的具体事实或需求）

## 变更内容

（改什么，改成什么）

## 影响分析

| 受影响产物 | 影响方式 | 需要返工的范围 | 预估工作量 |
|---|---|---|---|

参考 `document-map.yaml` 的 `impact_rules` 列出连带影响。

## 替代方案

（至少一个；说明为什么不选它）

## 如果错了的代价

## 决策

- [ ] 批准
- [ ] 拒绝
- [ ] 修改后批准

决策人：     决策时间：

## 执行记录

| 时间 | 动作 | 结果 |
|---|---|---|
```

## 4. 版本规则

| 产物类型 | 版本方式 |
|---|---|
| 原型 | 新目录 `v2/`，保留 `v1/` 作为历史 |
| PRD、设计文档 | 文件内加"修订记录"表，保留历史条目；重大改版另存新文件 |
| 数据库迁移脚本 | 新增 `V<n>__*.sql`，**禁止修改已执行的脚本** |
| 前端 / 后端代码 | 正常 Git 提交，提交信息带 CR 编号 |

## 5. 完成后动作

1. 更新 `file-catalog.md` 中受影响文件的状态
2. 更新 `traceability.yaml` 的链接
3. 在 `decisions.md` 追加一条 Ruling
4. 若涉及已冻结产物，把旧版本状态标为 `superseded`
5. 在下一批任务包中说明本次变更
