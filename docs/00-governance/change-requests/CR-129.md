# CR-129 — 阶段 6 第四十八批：四类主体删除接口接前端

第二轮队列第 7 项「主体删除接口」。用户 2026-10-10 明确要求 `DELETE` 类主体删除接口也要接前端（`D-204`，
覆盖此前 `D-199`～`D-202` 的暂缓结论），本批按 `D-204` 的四条约束落地。

## 1. 接法与位置

| 页面 | 入口 | 权限 | 接口 |
|---|---|---|---|
| 学生列表 `/edu/student/list` | 操作列「更多▾」→ 删除学生 | `person.student:remove` | `DELETE /edu/student/{id}?reason=` |
| 班级列表 `/edu/class/list` | 操作列「更多▾」→ 删除班级 | `org.class:remove` | `DELETE /edu/class/{id}?reason=` |
| 年级列表 `/edu/grade/list` | 操作列「更多▾」→ 删除年级 | `org.grade:remove` | `DELETE /edu/grade/{id}?reason=` |
| 学科列表 `/edu/subject/list` | 操作列「更多▾」→ 删除学科 | `org.subject:remove` | `DELETE /edu/subject/{id}?reason=` |

四条约束（`D-204`）：① 入口在「更多▾」下拉，不增加行内按钮；② 二次确认 + 必填删除原因；
③ 不做前端预判、不绕过后端校验，后端拒绝时原样展示后端错误信息；
④ 只做单条删除，不做批量、不物理级联。

**没有按原型做条件显隐**：`class-list.html` 原型只在「在读人数为 0」的行渲染删除入口、`grade-list.html` 只在空年级渲染。
本批按 `D-204` 的「不做前端预判」一律渲染入口，由后端拒绝并回传原因 —— 否则前端要复制一遍引用判断规则，
两份规则一定会漂移。

## 2. 后端补齐（stage 7 契约缺口）

| 问题 | 证据 | 处置 |
|---|---|---|
| `DELETE /edu/class/{id}`（`removeClass`）在 `openapi.yaml` 有声明，ruoyi-edu 无实现 | `EduClassController` 只有 `/{classId}/roster/{studentId}` 一个 `@DeleteMapping` | 补控制器 + 服务接口 + 实现；有在读学生 / 有任教关系时拒绝并提示改用停用（`REQ-CLS-043` / `REQ-CLS-046`） |
| `DELETE /edu/grade/{id}` 不接收 `reason` | `EduGradeController.remove(@PathVariable Long gradeId)` | 补 `@RequestParam(required = false) String reason`，与 student / subject / term 一致 |

## 3. 顺带修正

停用 / 归档原因的前端校验此前是「至少 2 个字」，后端 `disableClass` 要求 ≥5 —— 前端会放行一个后端必然拒绝的值。
本批把班级停用、年级归档、学科停用的前端校验统一为「至少 5 个字」，新增的四个删除入口同口径（GAP-107）。
