# CR-110 — 阶段 7 部署批：初始化 MinIO 桶，修复上传接口 500

用户上传文件报错：

```
org.dromara.common.oss.exception.OssException: 上传文件失败，请检查配置信息:[subscription has been cancelled.]
	at org.dromara.common.oss.core.OssClient.upload(OssClient.java:225)
	at org.dromara.common.oss.core.OssClient.uploadSuffix(OssClient.java:386)
	at org.dromara.resource.service.impl.SysOssServiceImpl.upload(SysOssServiceImpl.java:181)
```

## 1. 定位

| 检查 | 结果 |
|---|---|
| MinIO 容器 / 端口 | 容器 Up，`http://127.0.0.1:9000/minio/health/live` → 200，控制台 9001 → 200 |
| `sys_oss_config`（id=1，启用） | `endpoint=127.0.0.1:9000`、`bucket_name=ruoyi`、`access_key=ruoyi`、`secret_key=ruoyi123`、`is_https=N` —— 与 compose 的 `MINIO_ROOT_USER/PASSWORD` 一致 |
| `HEAD /ruoyi`（用同一套 AK/SK 走 SigV4） | **404**（桶不存在） |
| `PUT /ruoyi/probe.txt` | **`NoSuchBucket: The specified bucket does not exist`** |

结论：**不是网络/凭据问题**。`ruoyi-common-oss` 这一版走的是 AWS S3 异步 SDK（`S3AsyncClient`），
不像上游 MinIO SDK 那样在构造 `OssClient` 时 `createBucket`；docker-compose 起 MinIO 时也不会建桶 ——
两边都不建，于是 `PutObject` 报 `NoSuchBucket`，而 SDK 把它包成了
`subscription has been cancelled.`（真实错误被吞掉，很容易误判成连接超时）。

附带发现：`sys_oss_config.access_policy=1`（公开）**不会**自动给桶打策略，桶私有 → 上传虽然能成功，
但前端拿到 URL 后匿名访问 403、图片显示不出来（实测匿名 GET 403）。

## 2. 处置

| 落点 | 内容 |
|---|---|
| 本机 MinIO | 已创建 `ruoyi` 桶，并设置「公开只读」桶策略（`s3:GetObject` for `*`） |
| `services/RuoYi-Cloud-Plus/script/docker/init-minio-bucket.py`（新增） | 幂等初始化脚本：`headBucket` → 不存在则 `createBucket` → `putBucketPolicy` 公开只读；只依赖标准库；`--private` 可只建桶 |
| `services/RuoYi-Cloud-Plus/script/docker/README-deploy.md`（改） | 新增「## 2.1 初始化 MinIO 桶（必做，否则上传接口报错）」，写明错误特征、一行初始化命令与验证方式 |

## 3. 验证

## 4. 未改动项（及理由）

没有去改 `ruoyi-common-oss` 让它自动建桶：那是所有服务共用的 OSS 客户端，启动期做 `createBucket/putBucketPolicy`
会在扫描到未启用的样例配置（aliyun/qiniu/qcloud 占位行）时产生额外失败面；本批按「初始化脚本 + 部署手册」
落地（见 D-191）。如果以后要做到零手工，可在 `SysOssConfigServiceImpl.init()` 里对**启用的**配置做一次
「桶不存在则创建」的兜底，作为独立变更评估。
