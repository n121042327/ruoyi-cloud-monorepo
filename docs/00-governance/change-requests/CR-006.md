## 2. 变更原因

用户要求系统提供一个「可以做任意事、所有权限、所有功能、所有角色」的账号。
现存文档里最接近的是运营方租户的运营人员（`platform_ops`），
但 `BR-ORG-005` 明确规定运营方的「查看 / 修改 / 导出」是三项独立授权、缺一项即拒绝，
`PM-DENY-005` 还要求教育数据权限独立于系统租户管理员的放行逻辑。
因此**不能**简单地把 `platform_ops` 放宽，需要新增一个边界明确的系统内置角色。

## 3. 变更内容

### 3.1 角色定义

```yaml
  - code: super_admin
    name: 系统超级管理员
    home: system
    default_data_scope: platform
    note: |
      系统内置账号，不属于任何业务租户，由平台在部署时创建并按需授予（BR-ORG-014）。
      不受租户隔离、数据范围与功能权限限制，可执行全部功能；因此禁止用于日常业务操作。
      所有访问与写操作仍强制写审计（BR-AUDIT-001），审计不可关闭。
```

### 3.2 功能权限

对 22 个资源（`org.*`、`person.*`、`enrollment.*`、`promotion.batch`、`stream.*`、`data.*`、`audit.log`）
各授予全部 7 个操作（`read` / `create` / `update` / `delete` / `export` / `approve` / `import`）。

实现说明：**不使用通配符**。矩阵里逐条列出资源，是为了让评审者能一眼看出超级管理员到底能碰什么，
也避免后端实现时把「`*`」误解析成绕过所有校验（本次就有一条 `PM-DENY-*` 依赖这一层显式列举）。

### 3.3 数据范围

新增 `DP-07`：超级管理员在范围解析的第 0 步直接放行，不做范围解析，不按 `DS-01` ~ `DS-07` 收窄。
它是数据范围的**唯一例外**，不适用于任何业务角色。

### 3.4 边界（重要）

1. **仍然强制写审计**：访问留痕 + 写操作的变更前后值（`BR-AUDIT-001`、`BR-AUDIT-002`）。
   审计是合规底线，不是权限，因此不随超级管理员一起放开。
2. **禁止用于日常业务操作**：它的定位是部署初始化、应急处理、跨租户排障。
   日常编班、导入、年级维护等仍由教务主任等业务角色执行（`D-042`「每个字段只有一个写入入口」）。
3. **与平台运营是两类主体**：`platform_ops` 是运营方租户里的运营人员，仍按查看 / 修改 / 导出分别授权；
   超级管理员是系统内置账号。`BR-ORG-014` 明确它是 `BR-ORG-005` 的唯一例外。
4. **不参与场景覆盖矩阵**：为避免把应急账号误读成业务角色，覆盖矩阵不单列一列。

## 5. 替代方案

- 把 `platform_ops` 直接放宽为全权限：与 `BR-ORG-005`、`PM-DENY-005` 冲突，
  且会让日常使用的运营账号永久持有跨租户写权限，风险最大的做法。
- 只加角色不加审计：会失去「谁在什么时候改了什么」的唯一追溯手段，
  与 `CTX-GOAL-06`「关键写操作 100% 有日志」冲突。
- 只加角色不写这条规则：矩阵里会出现一个没有业务规则支撑的角色，
  阶段 6 的前端守卫与阶段 8 的用例都无法判定。

## 6. 如果错了的代价

收回 `super_admin` 的授权行并停用该账号即可；审计记录已产生，属于不可撤销的正常代价，不需要回滚数据。
若要改为「连审计也跳过」，改动只在日志层，不影响原型与表结构。
