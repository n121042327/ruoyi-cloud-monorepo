## D-001 阶段流水线固定为九阶段

- 状态：已确认
- 决策：项目核查与工程约束 → PRD → 业务原型 → 独立高保真原型 → 概要设计 → 详细设计及建表 → 生产前端 → 生产后端 → 联调验收

## D-003 monorepo + Turbo + 目标目录 apps/ 与 services/

- 状态：已执行（2026-09-29）
- 决策：根仓库统一管理；前端放 `apps/plus-ui`，后端放 `services/RuoYi-Cloud-Plus`
- 理由：用户要求 monorepo、Turbo 加速，并为后续移动端预留位置
- 如果错了的代价：目录迁移涉及移动含内层 Git 元数据的目录，处理不慎会丢历史
- 实际执行：内层 `.git` / `.git1` 由用户先行删除并暂存（pack 归档在根仓库）；两个目录以 `git mv` 迁移，Git 识别 1622 条改名，历史连续
- 结果：`apps/plus-ui/` 与 `services/RuoYi-Cloud-Plus/` 已就位

## D-004 后端用微服务框架但教育能力单模块承载

- 状态：已确认
- 决策：在 `ruoyi-modules` 下新增 `ruoyi-edu`，四个首轮模块（年级 / 班级 / 教师 / 学生）不各拆一个微服务
- 理由：四个模块共享大量关系（学生—班级—年级—学校），拆开会产生大量跨服务事务
- 如果错了的代价：单模块后续变大，需要按领域再拆；拆分成本低于初期过度拆分的协调成本

## D-005 教育表与系统表同库不混用

- 如果错了的代价：同库容易产生"顺手 join 一下"的越界写法，需要靠 Code Review 和测试守住

## D-010 升班与 3+1+2 纳入首轮设计并实现

- 状态：已确认
- 决策：升班必须支持预览、校验、确认、异步执行、结果查看、失败重试，并保证幂等；"3+1+2"为物理 / 历史二选一，化学 / 生物 / 思想政治 / 地理四选二，选科带生效学年学期与变更历史
- 理由：用户明确要求纳入设计并实现
- 如果错了的代价：这是首轮最复杂的能力，实现成本高；但延后会导致表结构返工

## D-011 数据权限四层模型

- 状态：已确认
- 决策：校领导看本校全部；年级主任看负责年级；班主任看负责班级；任课教师看本人任教班级必要资料与本人所授学科数据；集团不自动获得学校教学数据；平台运营全平台可见但查询 / 修改 / 导出分别授权
- 理由：用户明确描述
- 如果错了的代价：权限放大是安全事件，必须靠越权测试兜底

## D-012 首轮不跨校共享

- 状态：已确认

- 如果错了的代价：后续要支持跨校时需要重新梳理数据范围，属架构层改动
- 缓解：数据范围模型在设计阶段就预留 `scope_type` 维度

## D-013 执行方式：小批 + 人工验收 + 不自动提交

- 状态：已确认
- 决策：每批 2—3 个页面或 1 个服务模块；每批暂停等用户验收；不自动 commit、不自动 push
- 理由：用户明确要求
- 与技能默认行为的差异：`executing-plans` 技能默认"持续执行、自行裁决、按计划提交"。
  **本项目以用户要求为准**：暂停点保留、提交动作改为"展示变更摘要后等指令"。
- 注明：该差异由用户指令产生，不是技能要求。

## D-024 前端质量门禁按"不新增错误"执行

- 状态：已确认
- 背景：基线检查发现上游既有代码有 49 个 TypeScript 错误与 125 个 Lint 问题（详见 `repo-baseline.md` 第 12 节）
- 决策：教育模块的验收门禁为"新增代码零错误 + 既有错误数不增加"；上游遗留清理单独排期
- 理由：把上游历史问题卷进首轮交付，会稀释验收信号，且改动面与交付内容无关
- 如果错了的代价：首轮结束时仓库整体仍不是"零错误"状态，需要在交付说明中明确标注
- 记录方式：每次阶段 6 批次结束，把 typecheck 与 lint 的错误总数写入 `evidence/`，与基线对比
